## Session context

Events are captured and stored (4.1–4.4). This step makes the timeline **readable
back** — for humans, scoring, and reports. DuckDB queries the Parquet partitions
(scoped via the Postgres index from 4.2); a replay reconstructs a run as one
ordered timeline of typed events; and `range trace` renders the interleaved
model + host (+ network) story. The `timeline` renderer is the demo's **"watch the
agent work"** view.

## Goal

A run can be replayed as **one coherent, correctly-ordered timeline**.

## Scope (build this)

- `trace/query.py`: DuckDB over the Parquet glob + the Postgres run index — typed
  query helpers (events for a run, by source, by time/step range, joins).
- `trace/replay.py`: reconstruct a run as a single ordered timeline of typed
  `Event`s (deterministic order via the §8 key).
- `cli`: `range trace <run_id> [--source …] [--follow] [--format
  table|json|timeline]`.

## Out of scope

- Dashboards / web UI (future, B-18); ML analytics (future, B-16/B-17);
  aggregation across runs (7.3 — which *uses* this).

## Implementation details

### `trace/query.py`
- A DuckDB connection that **attaches the Parquet glob** for a run
  (`{root}/run_id=<rid>/source=*/part-*.parquet`) and reads the **Postgres index**
  for scoping (which parts/time ranges exist). When object storage is enabled
  (4.2), DuckDB reads via the S3-compatible endpoint; otherwise local files.
- **Typed, parameterized** query helpers (no string interpolation of user input):
  - `events_for_run(run_id) -> list[Event]`
  - `events_by_source(run_id, source) -> list[Event]`
  - `events_in_step_range(run_id, lo, hi)` / `events_in_time_range(...)`
  - a couple of join helpers (e.g. model tool_call ↔ resulting host process events
    in the same step window) — keep to what reports/demo actually need (YAGNI).
- **Read-only**: no helper mutates state.

### `trace/replay.py`
- `replay(run_id) -> list[Event]`: load all events for the run, sort by the §8
  **ordering key** `(wall, step_seq, source_seq)` → a **deterministic** single
  timeline. Repeated calls yield identical ordering.
- A small `TimelineEntry` view (or reuse `Event`) carrying enough for rendering.

### `cli` — `range trace`
```python
@app.command()
def trace(
    run_id: str = typer.Argument(...),
    source: list[str] = typer.Option(None, "--source", help="Filter: model/host/network/..."),
    follow: bool = typer.Option(False, "--follow", help="Stream as events arrive."),
    fmt: str = typer.Option("timeline", "--format", help="table|json|timeline"),
) -> None:
    """Replay a run's unified timeline."""
```
- `timeline` (default): a human-readable, interleaved render — step → model
  action → resulting host/network events — the demo's "watch the agent work" view.
- `table`: columnar; `json`: machine-readable (for piping).
- `--follow`: stream as events arrive (pairs with 4.3's live hooks); for a
  finished run it just renders then exits.

## Infrastructure (Terraform)

- **None.** DuckDB is an in-process library on the control plane (the 0.3 host); it
  queries the **block-volume Parquet** (or the optional **object-storage** bucket
  from 4.2 via the S3 endpoint) plus the compose **Postgres** index. No new OCI
  resource. If object storage is enabled, ensure DuckDB's `httpfs`/S3 settings use
  the same endpoint + out-of-band credentials as the store (4.2) — don't duplicate
  the config.
- `@pytest.mark.postgres`/`docker` query tests run on the host (or any machine with
  the compose Postgres + Parquet present).

## Testing

**Unit (`test_replay_ordering.py`, runs in CI):**
- Given a synthetic mixed-source event set (built via 4.1 + written to local
  Parquet via 4.2's local path), `replay` returns a **total, deterministic**
  ordering by the §8 key; repeated calls are identical; ties broken by
  `source_seq`.
- `test_trace_cmd.py`: `range trace` with each `--format` renders without error on
  a small fixture run; `--source` filters correctly.

**Integration (`@pytest.mark.postgres`/`docker`):**
- After a real run (3.4 path or a seeded store), `range trace <run_id>`
  reconstructs the **full ordered timeline**; `events_by_source` / step-range
  queries return correct slices; ordering is deterministic across repeated calls.
