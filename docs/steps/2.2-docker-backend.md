## Session context

The `Backend` seam + fake backend exist (2.1). This step writes the **first real
backend**: turn a scenario's hosts into actual, isolated Docker containers on the
**OCI host from Step 0.3** (Docker + `runsc` already installed there). Networking,
gVisor hardening, images, and snapshots are *later* steps — here we just stand
hosts up as containers, exec into them, move files, and tear down **without
leaking anything**.

## Goal

A multi-host scenario stands up as containers on the OCI host and tears down
cleanly (verified: zero resources left by label).

## Scope (build this)

- `provision/docker/backend.py` — `DockerBackend(Backend)` over the Docker SDK
  (`docker-py`): per-host container from the host's (digest-pinned) image;
  label every resource with `run_id`/`scenario_id`; `exec` via
  `container.exec_run` (thread-offloaded); `copy_in/out` via tar streams;
  idempotent `teardown` by label; readiness wait.
- `provision/docker/__init__.py` — self-register the backend in the registry as
  `"docker"`.

## Out of scope

- Subnets/routing/egress (2.3), gVisor runtime + hardening (2.4 — here containers
  may run on the default runtime; 2.4 switches them to `runsc` and hardens),
  image building (2.5 — use simple pinned images for now), snapshot (2.6).

## Implementation details

- **Blocking SDK calls are offloaded** to a thread (`asyncio.to_thread`) so the
  async `Backend` contract holds.
- Container naming: `range-<run_id>-<host_id>`; **labels** on every container
  (and later network/volume): `range.run_id`, `range.scenario_id`,
  `range.host_id`, `range.managed = "true"`. Labels are the discovery + cleanup
  key.
- `provision`: pull/resolve each host's digest-pinned image, create + start the
  container with resource limits from the spec (`nano_cpus` from `resources.cpu`,
  `mem_limit` from `resources.memory_mb`), set `env`. **Readiness** = container
  running + optional per-host healthcheck; wait with a bounded timeout.
- `exec`: `exec_run(argv, user=..., demux=True)` → map to `ExecResult` (stdout,
  stderr, exit_code, duration). `copy_in/out`: tar stream via
  `put_archive`/`get_archive`.
- **`teardown` must be exhaustive and idempotent** — stop + remove **all**
  resources matching the run labels, even on a *partial* provision failure. Use a
  **finalizer pattern**: register cleanup as each resource is created so a failure
  mid-`provision` still cleans up. Tearing down an already-gone range is a no-op.
- All Docker failures wrapped as `ProvisionError`/`BackendError` carrying the
  docker error context (no bare excepts; no leaking SDK exceptions upward).
- Emit lifecycle + exec events to the injected trace sink with correlation IDs
  (same events the fake emits — so the trace layer is backend-agnostic).

## Testing

**Unit (`test_backend_unit.py`, mocked SDK — runs in CI):**
- argv/exec mapping → `ExecResult`; label construction; resource-limit
  translation; the finalizer registers cleanup for each created resource;
  `teardown` issues removes for exactly the labelled set; SDK errors become
  `ProvisionError`/`BackendError`.

**Integration (`@pytest.mark.docker`, on the OCI host):**
- Reuse the **backend-contract fixture from 2.1** against `DockerBackend`.
- Provision a 2-host scenario; `exec whoami`; `copy_in` a file and `copy_out` it
  back (bytes match); `teardown` leaves **nothing** — assert by querying Docker
  for the run labels and getting an empty set.
- Partial-failure cleanup: force a failure mid-provision (e.g. a bad image on the
  2nd host) and assert the 1st host's container was still cleaned up.
