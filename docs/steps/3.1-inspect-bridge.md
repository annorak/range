# Step 3.1 — Inspect bridge: scenario → Task + Range SandboxEnvironment  `[MVP]`

> **Claude Code session prompt.** Self-contained. Read
> `docs/steps/_SHARED_STANDARDS.md` first.
>
> ⚠️ **High-risk seam.** This is the load-bearing integration with **Inspect AI**:
> a custom `SandboxEnvironment` that routes Inspect's tool execution into a
> Range-provisioned range. Get it conformant to Inspect's ABC *exactly* so all of
> Inspect's machinery (solvers, transcripts, model providers, compaction) works
> unmodified. Pin the Inspect version and treat its ABC as the contract.

## Session context

The spec parses/validates/scores (Epic 1) and the provisioner can stand up a range
on the fake and Docker backends (Epic 2). Now we make a Range scenario **runnable
by Inspect**: map a `Scenario` → an Inspect `Task`, and implement a custom
**`SandboxEnvironment`** whose `exec`/`read_file`/`write_file` route to the Range
`Backend` against the attacker host, with provision/teardown wired into the
sandbox lifecycle. This is what lets the rest of Inspect (and the attacker agent
in 3.2) run against a real multi-host range.

## Goal

`inspect eval` drives a Range scenario and tool calls land **inside** the range;
teardown always fires.

## Scope (build this)

- `inspect_bridge/task.py`: `scenario_to_task(scenario, *, backend, ...) -> Task`
  — build an Inspect `Task` with a `Dataset`/`Sample` carrying the objective +
  milestone metadata.
- `inspect_bridge/sandbox.py`: a custom Inspect **`SandboxEnvironment`** backed by
  the Range `Backend`; Inspect's `exec`/`read_file`/`write_file` → `Backend.exec`/
  `copy_out`/`copy_in` against the `role=entry` host by default; sandbox lifecycle
  hooks call `provision`/`teardown`. **Register** the sandbox provider with
  Inspect.
- `docs/adr/0006-inspect-sandbox-abc.md`: pin the Inspect version + document the
  exact ABC surface we depend on.

## Out of scope

- The agent loop / toolbox (3.2), scoring (3.3), the end-to-end `range run` (3.4),
  multi-agent (5.x). Multi-host exec *from a tool* (choosing a non-entry host) is a
  3.2 tool — here the sandbox defaults to the entry host.

## Implementation details

> **Conform to the installed Inspect version, not to this doc.** The method names
> below reflect Inspect's `SandboxEnvironment` ABC shape; **verify each signature
> against the pinned version** and match it exactly. If the pinned API differs,
> the installed package wins — update this step's notes + ADR 0006 to match.

### `inspect_bridge/sandbox.py` — `RangeSandbox(SandboxEnvironment)`
- Implement the ABC's **instance methods**, delegating to the Range `Backend`:
  - `async exec(cmd, input=..., cwd=..., env=..., user=..., timeout=...) ->
    ExecResult` → `Backend.exec(handle, host_id=<entry>, argv=cmd, ...)`; map
    Range's `ExecResult` → Inspect's exec-result type (stdout/stderr/exit/success).
  - `async read_file(file, text=True) -> str | bytes` → `Backend.copy_out`.
  - `async write_file(file, contents)` → `Backend.copy_in`.
  - any other required ABC members (e.g. connection/info) — implement minimally.
- Implement the **lifecycle class methods** Inspect calls (verify names —
  typically `task_init` / `sample_init` / `sample_cleanup` / `task_cleanup`, plus
  `config_files` / `default_concurrency` if required):
  - **provision** the range in sample setup → store the `RangeHandle` keyed by the
    sample, return the mapping of sandbox name(s) → instance.
  - **teardown** in cleanup via a **finalizer** so teardown fires even if the eval
    errors (mirror the 2.2 exhaustive-cleanup contract).
- The sandbox targets the `role=entry` host by default. Thread `CorrelationIds`
  and the injected **trace sink** through every `Backend` call (the agent's
  multi-host tool in 3.2 reuses this path).
- **Register** the provider so `sandbox="range"` (or the chosen provider name)
  resolves to `RangeSandbox` — follow Inspect's sandbox-registration mechanism.

### `inspect_bridge/task.py` — `scenario_to_task`
- Build a `Task` with:
  - a `Dataset` of one `Sample` (v1 single-objective) whose `input` is the
    attacker objective and whose `metadata` carries `scenario_id`, the milestone
    list, and the host map — so the scorer (3.3) and trace can read them.
  - `sandbox` set to the Range provider, parameterized with the chosen backend
    (`fake`|`docker`) + the scenario (so sample setup can provision).
  - `solver`/`scorer` left as injection points (3.2 supplies the attacker solver;
    3.3 the scorer) — **do not** hardcode them here.
- Keep the mapping pure and deterministic (seeded where relevant).

### ADR 0006
Record: the pinned Inspect version; the exact `SandboxEnvironment` members we
implement; the registration mechanism; and the note that an Inspect upgrade
requires re-checking this surface (additive-only on our side).

## Infrastructure (Terraform)

- **No new OCI resource.** The bridge runs on the 0.3 host. It introduces the
  runtime need for **model-provider API access**:
  - **Egress** to model APIs over 443 is already permitted by the 0.3 NSG — no
    change. (Range *containers* remain egress-denied; only the control-plane
    process calls model APIs.)
  - **Secrets**: `RANGE_ANTHROPIC_API_KEY` / `RANGE_OPENAI_API_KEY` are read via
    `config.Settings` (`SecretStr`, from 0.2). Supply them on the host as
    environment (e.g. a root-owned env file sourced by the run, or your shell
    profile) — **never** baked into an image, committed, or placed in Terraform
    state. A managed secret store (OCI Vault) is future work (backlog **B-34**).
- The `@pytest.mark.docker` eval test runs on the OCI host; the fake-backend tests
  run anywhere (CI).

## Testing

**Unit (fake backend — runs in CI):**
- `scenario_to_task` produces a `Task` with the expected sample metadata
  (objective, `scenario_id`, milestones, host map).
- `RangeSandbox.exec/read_file/write_file` route to the fake backend correctly
  (assert via the fake's recorded calls); result mapping is faithful.
- **Lifecycle**: an Inspect eval with a **stub solver** that execs one command and
  reads a planted flag runs end-to-end on the fake backend; **teardown always
  fires** — including when the solver raises (force an error, assert teardown ran).

**Integration (`@pytest.mark.docker`, on the OCI host):**
- The same stub-solver eval against a real **1-host** range: the command executes
  inside the container, the flag is read, teardown leaves nothing (label-verified).
